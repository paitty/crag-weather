# Working conventions for this repo

Practical notes for future Claude Code sessions on `crag-weather`, based on
lessons learned while iterating on `generate_crag_weather_html.py`.

## Git workflow

- Work happens on a feature branch first, then gets merged into `main`.
  Don't push straight to `main` without going through this.
- Before committing/pushing anything non-trivial (especially anything that
  changes visible output like icons, colors, table layout), show the user
  the diff/plan and get explicit confirmation first. Only proceed to
  commit+push+merge once they say go ahead. This applies per change, not
  once for the whole session — don't batch up multiple unrelated changes
  under one earlier approval.
- To merge into `main`: `git fetch origin main`, `git checkout main`,
  `git pull`, `git merge --no-ff <feature-branch>`, `git push origin main`,
  then switch back to the feature branch.
- **Expect merge conflicts in generated/data files** — `build_outputs_folder/*.html`,
  `generated.txt`, `*-table.json`, `ambrozija-table.json`. Both `main` and
  the feature branch independently run the GitHub Action, so these files
  drift apart. It's always safe to resolve these by keeping `main`'s
  version (`git checkout --ours -- <file>`) since they get regenerated by
  the next workflow run regardless — just make sure the actual *code*
  changes (`.py`, `.gitignore`, workflow YAML) merge in cleanly.
- Before pushing, `git fetch` the target branch first — the GitHub Action
  commits directly to whichever branch it runs on (`git pull && git add . &&
  git commit && git push` inside the workflow), so branches move on their
  own between your local checkouts. Rebase/fast-forward as needed.

## Testing changes (no local network access)

This sandboxed environment **cannot reach** `api.met.no`, the OSRM router,
`bergfex.com`, or CDNs like `cdn.jsdelivr.net` — the script cannot actually
be run end-to-end locally. `raw.githubusercontent.com` **is** reachable
(via `curl` or `WebFetch`), which is enough to pull real generated output
back down for inspection after a workflow run.

To test a change:
1. Push the change to the feature branch.
2. Trigger the workflow manually: `.github/workflows/main.yml` has a
   `workflow_dispatch` trigger (added specifically for this) — use the
   GitHub Actions API/MCP tools to dispatch it on the feature branch.
3. The `deploy` job **will fail on any branch except `main`** — GitHub
   Pages' environment protection rules restrict deploys to `main` only.
   This is expected, not a bug; only check the `build` job's result.
4. Once `build` succeeds, fetch the regenerated files (e.g.
   `build_outputs_folder/climbing_detail_footprint.html`,
   `skiing_detail_footprint.html`) via `raw.githubusercontent.com/<owner>/<repo>/<branch-or-sha>/<path>`
   to inspect the actual output.

## Showing the user the result

- The Artifact tool **cannot** render these pages — they depend on external
  CDN resources (Leaflet, jQuery, Bootstrap, Font Awesome, OpenStreetMap
  tiles) and Artifacts run under a strict CSP that blocks all outside
  network requests. Publishing one just shows a blank page.
- Instead, send the generated `.html` file(s) directly to the user (e.g.
  via `SendUserFile`) so they can open it in a real mobile/desktop browser,
  which isn't sandboxed.

## Icons on the map/table

- Prefer **plain emoji** over Font Awesome icon-font glyphs for marker/table
  icons. Font Awesome icons (via folium's `BeautifyIcon`) failed to render
  on at least one real device — showing just the bare pin/disk with no
  glyph — likely a web-font loading issue. Emoji need no external font and
  render natively everywhere.
- Map marker color/icon logic lives in `display_cities_on_map()` in
  `generate_crag_weather_html.py`, driven by the same `Temp_style` /
  `Wind_style` / `Rain_style` threshold flags already used for the table.
  Keep icon and color derived from the *same* category check so they never
  disagree (e.g. a green "all ok" marker never shows a rain icon).

## `.gitignore` history

`build_outputs_folder/climbing_detail_footprint.html`,
`skiing_detail_footprint.html`, and `skiing_index.html` were accidentally
`.gitignore`d from the very first commit of that file, so those generated
outputs were silently never committed for a long time (fixed). If a
generated file mysteriously stops showing up in commits again, check
`.gitignore` first before assuming the script is broken.
